Professional Growth and Goals

Completing the Computer Science program at Southern New Hampshire University has changed the way I approach technical problems. Earlier in the program, I often focused mainly on getting code to work. I now begin by understanding the problem, the people who will use the solution, the data that must be protected, and the way the software will be tested and maintained. My coursework and capstone ePortfolio show this growth. They also show that I can take an older project, evaluate its weaknesses, plan improvements, and produce a stronger solution.

My professional goal is to move into software engineering with a focus on warehouse automation, web applications, and database systems. My current work in the AutoStore field has given me practical experience with automated equipment, system logs, settings, error messages, maintenance, testing, and commissioning. This experience has shown me how important reliable software is in a working warehouse. A small software problem can affect equipment, inventory, employees, and customer operations. Because of this, I value safety, security, accuracy, organization, accountability, and continuous improvement.

The Computer Science program helped me connect these professional values to software development. I learned that a successful solution is not only one that runs. It must also be understandable, secure, efficient, and useful to the people who depend on it. I am prepared to continue building my skills in Python, databases, testing, security, and automation. In the future, I also want to learn more about using artificial intelligence and connected devices for predictive maintenance, equipment monitoring, inventory forecasting, and faster troubleshooting.

Collaboration and Communication

Working in warehouse automation has taught me that technical problems are rarely solved by one person. I work with technicians, engineers, managers, and customer teams. During troubleshooting, I review logs, settings, and error messages before recommending a change. I share the evidence with the people involved, listen to their observations, discuss the possible impact, and help select a safe next step. After a change is made, the team tests the system and confirms the result. This process supports better decisions because it combines different types of experience instead of depending on one point of view.

I have also learned to adjust my communication for different audiences. Another technician may need exact error information and detailed testing steps. A manager may need a short explanation of the risk, expected downtime, and available options. A customer may need a clear explanation without unnecessary technical terms. My experience with customer training, service reports, checklists, and operating procedures has helped me communicate technical information in a useful way. It has also taught me to ask questions and confirm understanding instead of assuming that everyone has the same background.

My coursework strengthened these skills through project discussions, written assignments, presentations, and code reviews. For this capstone, my code review video presents the original application, explains its strengths and weaknesses, and describes the planned enhancements. The written narratives explain the same work in more detail. Together, these items show my ability to use oral, written, and visual communication. They also show that I can explain technical decisions to both technical and nontechnical audiences.

Data Structures and Algorithms

My studies in data structures and algorithms taught me to think beyond whether a feature works. I now consider how data is organized, how many records the program must process, and how the choice of an algorithm affects speed and memory. Across my programming coursework, I practiced breaking larger problems into smaller steps and comparing possible solutions before selecting one. This way of thinking is important in warehouse systems because inventory data can grow quickly and users still expect fast results.

The search enhancement in my ePortfolio is one example. The application cleans the search value, limits its length, treats special search symbols as normal text, and performs the search inside SQLite. It ranks an exact item name first, a name that begins with the search text second, and a name that contains the text in another position after that. Pagination returns only the records needed for the current page. I also used immutable data classes and tuple results so search data cannot be changed by accident after it is created.

I evaluated the performance of this solution instead of only describing the code. The database examines matching records and sorts the result, which can be described as O(n + m log m), where n is the number of records examined and m is the number of matches. The final page transfer is O(k), where k is the small number of records displayed. I also recognized the tradeoff between a contains search, which is more flexible, and a prefix search, which can use an index more efficiently. This shows that I can evaluate a solution and explain why one design may be better for a specific situation.

Software Engineering and Database Development

The program helped me develop a complete view of the software development process. In CS 360, I created the original Android inventory application with Java, XML, and SQLite. That course helped me understand mobile interfaces, user input, and local data storage. In CS 320, I practiced software testing and quality assurance. I learned to define requirements, create unit tests, and use test results as evidence. In CS 340, I strengthened my understanding of database design, SQL, and create, read, update, and delete operations. These experiences prepared me to combine interface design, program logic, testing, and data management in the capstone.

For the capstone, I converted the Android application into a browser application built with Python, HTML, CSS, and SQLite. I separated the application into files for routes, services, database access, models, validation, security, templates, styling, and the database schema. This structure makes the program easier to read, test, maintain, and expand. It also supports reusable code because each part has a clear responsibility. The application includes account registration, login, inventory management, user ownership, search, pagination, activity history, and a dashboard report.

The database enhancement added foreign keys, constraints, transactions, indexes, and an inventory activity table. Each inventory change creates a history record with a snapshot of the important values. Transactions keep the inventory change and history record together. If one part fails, the database rolls back the full operation. Composite indexes support common search and reporting requests. These choices improve reliability, traceability, and performance. The completed application has eleven passing automated tests, compared with four tests after the first enhancement and nine after the second enhancement. This test growth shows that I added verification as the application became more complex.

Security Mindset

Security is now part of how I plan a solution from the beginning. I do not view it as a final feature that can be added after development. I consider what data is sensitive, who should be allowed to access it, how input could be misused, and what could happen when an operation fails. This mindset is useful in both software development and warehouse automation because unreliable or unauthorized changes can affect real equipment and business operations.

The enhanced inventory application uses password hashing with PBKDF2 and 310,000 iterations, secure random session tokens, session expiration, request protection, input validation, parameterized SQL statements, escaped output, and ownership checks. The database also uses constraints and foreign keys to protect data relationships. Activity reports are limited to the signed in user, which protects the privacy of other accounts. Error handling and transactions help the application fail safely instead of leaving incomplete data.

My security learning also includes recognizing that no project is ever completely finished. A production release would still need secure hosting, encrypted network traffic, stronger cookie settings, request rate limits, monitoring, backups, and continued updates. Identifying these needs is part of responsible development. It shows that I can be honest about the current limits of a solution while planning the next improvements.

Algorithms and Data Structures Enhancement

This enhancement improved the way users search and move through large inventory lists.

Completed Enhancement

The application cleans the search value, removes unnecessary spaces, limits the search to 80 characters, and performs the search inside SQLite. The search is case insensitive and safely treats the percent sign, underscore, and backslash as normal text when the user enters them.

Ranking places an exact item name first, a name that begins with the search value second, and a name containing the value in another position after that. Pagination limits the results to ten records on each page and corrects page values that are outside the valid range. The InventorySearchPage and InventorySummary data structures keep related values together. Frozen data classes and tuple results help prevent accidental changes.

The database search and result sorting can be described as O(n + m log m), where n is the number of records examined and m is the number of matching records. Transferring the current page is O(k), where k is the small number of displayed records. Nine automated tests verified this stage of the application.

Database Enhancement

This enhancement added reliable activity history, reporting, privacy controls, and stronger database protection.

Completed Enhancement

I added an inventory activity table that records create, update, and delete actions. Each history record stores important inventory values so deleted or changed information can still be reviewed. Foreign keys and database constraints protect relationships and prevent invalid quantities.

Transactions keep an inventory change and its history record together. If either part fails, the full operation is rolled back. The dashboard report summarizes inventory activity for the signed in user while ownership checks protect the information of other users. Composite indexes improve common search and report requests.

The final application contains eleven passing automated tests. These tests verify account security, inventory operations, search behavior, pagination, transactions, activity history, reporting, privacy, and rollback behavior.
