Professional Growth and Goals

Completing the computer science program at Southern New Hampshire University has changed the way I approach technical problems. When I started the program, my main concern was usually getting the codes to work. If the application ran and produced the correct result, I often consider the work complete. As I moved through the program, I learned that working code is only part of a successful solution. I now think about the people using the application, the information it stores, the security risk and how the software will be tested and maintained.

The capstone gave me an opportunity to bring these lessons together. I returned to an older inventory application and reviewed it with the knowledge I have now. Instead of only looking at what worked, I looked for weaknesses in areas that could be improved. I then created the plan, completed the enhancement, tested the results, and explained the decisions I made. My professional goal is to move into software engineering and focus on warehouse automation, web applications, and database systems. My current work in the Automation field has already given me practical experience with automated equipment, system logs, settings, error messages, maintenance, testing, and commissioning. I have seen how a small software problem can affect equipment, inventory, employees, and customer operations.

In a working warehouse, reliability is not only a technical concern. It can have a direct effect on the entire operation. My work experience has also taught me to value safety, accuracy, organization, security, and accountability. The computer science program helped me connect those values to software development and now understand that good software should be secure, understandable, efficient and useful to the people who depend on it. I plan to continue improving my skills in Python and all other programming languages, databases, testing, security and automation. In the future, I would also like to learn more about artificial intelligence and connected devices. I’m especially interested in how these technologies can support predictive maintenance, equipment monitoring, inventory focusing, and faster troubleshooting in automated warehouses. My other plan is to increase my experience and knowledge in PLC (Programmable Logic Controller) for automation industries.

Collaboration and Communication

Working in warehouse automation has taught me that technical problems are rarely solved by one person. I regularly work with technicians, engineers, managers, and customer teams. Each person may notice a different part of the problem. A system log may contain an error code, while an operator may provide important information about what happened before the error appeared. When I troubleshoot a problem, I start by reviewing the available evidence, including logs, settings and error messages. I also listen to what other technicians and customers observed. I try not to recommend a change based on only one clue or one person’s opinion. After reviewing the information, the team discusses the possible risks and selects a safe next step. Once the change is made, we test the system and confirm whether the problem has been corrected.

I have also learned that the same technical problem must be explained differently depending on the audience. Another technician may need exact error messages, system settings and detailed testing steps. A manager may mainly need to understand the risk. Possible downtime and available options. A customer may need a clear explanation without too many technical terms. One lesson I have learned is that good technical communication does not mean giving everyone every available detail. It means giving each person the information they need to understand the situation and decide. My experience with customer training, service reports, checklist commissioning, troubleshooting and operating procedures has helped me improve in this area.

I have also learned to ask questions and confirm understanding instead of assuming that everyone has the same technical background. My coursework gave me more opportunities to practice oral and visual communication. For the capstone, I created a code review video that explained the original inventory application, its strengths, its weaknesses and my planned improvements. Recording the video required me to explain my ideas clearly instead of only showing the code. The written narratives allowed me to provide more detail about the decisions, challenges, and results of each enhancement.

Data Structures and Algorithms

My studies in data structures and algorithms changed the way I think about application features. In the past, I might have viewed a search feature as successful as long as it returned a result. I now consider how the data is organized, how many records the program must process, and how the selected algorithm affects speed and memory. This is especially important in warehouse systems because inventory data can grow quickly. A feature that works well with a few records may become slow when the database contains thousands of records. Users still expect the system to respond quickly, even when the amount of data increases.

The search enhancement in my ePortfolio is one example of how I applied this knowledge. When the user enters a search value, the application cleans the text and limits its length. It also treats special search symbols as normal text. The search is performed inside SQLite instead of loading every inventory record into the browser. The application ranks the results based on how closely they match the search. An exact item name appears first. An item name that begins with the search value appears next. Names containing the search value in another position appear after those results. This makes the search more useful because the most relevant items are displayed first.

I also added pagination so the application returns only the records needed for the current page. This reduces the amount of information transferred from the database and prevents the browser from loading every matching record at once. Immutable data classes and tuple results are used so the search information cannot be changed accidentally after it has been created. I evaluated the performance of the search instead of only confirming that it worked. The database examines the matching records and sorts the results. This can be described as O(n + m log m), where n represents the number of records examined and m represents the number of matching records. Transferring the final page is O(k), where k represents the small number of records displayed on the page.

I also considered the tradeoff between different search methods. A contains search is flexible because it can find the search value anywhere in the item name. However, a prefix search can use an index more efficiently because it searches from the beginning of the value. The best choice depends on what users need and how much data the system must process.

Software Engineering and Database Development

Several courses contributed to the way I completed the capstone project. In CS 360, I created the original Android inventory application using Java, XML, and SQLite. That course introduced me to mobile interfaces, user input, and local data storage. In CS 320, I learned more about software testing and quality assurance. I practiced reviewing requirements, writing unit tests, and using test results as evidence that the software behaves correctly. CS 340 helped me improve my knowledge of database design, SQL, and create, read, update, and delete operations. Each course gave me a different part of the development process. The capstone required me to combine those areas into one project. I had to think about the interface, program logic, database structure, security, testing, and the experience of the person using the application.

For the capstone, I converted the original Android application into a browser application using Python, HTML, CSS, and SQLite. I did more than move the same features from one platform to another. I reorganized the application so that each major responsibility has its own place. The project contains separate files for routes, services, database access, models, validation, security, templates, styling, and the database schema. This makes the application easier to read and maintain. It also makes testing easier because the program logic is not placed inside one large file. The completed browser application includes account registration, login, inventory management, user ownership, search, pagination, activity history, and a dashboard report. Separating these responsibilities gives the project a better foundation for future improvements.

The database enhancement added foreign keys, constraints, transactions, indexes, and an inventory activity table. Whenever an inventory item is changed, the application creates a history record containing a snapshot of the important values. This provides a record of what changed and helps make inventory activity easier to review. Transactions keep the inventory update and its history record together. If one part of the operation fails, the database rolls back the entire operation. This prevents an inventory item from being changed without a matching history record. Composite indexes were also added to support common search and reporting requests.

Testing was included throughout the enhancement process. The completed application has eleven passing automated tests. The first enhancement had four tests, and the second enhancement increased the total to nine. As the application became more complex, I added more tests to verify the new behavior. This helped me find problems earlier and gave me evidence that the main features continued to work after each change.

Developing a Security Mindset

One of the biggest changes in my thinking is that I no longer see security as something that should be added at the end of a project. I now consider security while planning the application. I ask what information must be protected, who should have access to it, how someone could misuse the input fields, and what should happen if an operation fails. This way of thinking is important in both software development and warehouse automation.

Unauthorized or unreliable changes can affect real equipment and business operations. Even a small inventory application must protect user accounts and prevent one user from accessing another user’s information.

The enhanced application uses PBKDF2 with 310,000 iterations to hash passwords. It also uses secure random session tokens, session expiration, request protection, input validation, parameterized SQL statements, escaped output, and ownership checks. These protections work together instead of depending on only one security control. The database uses constraints and foreign keys to protect relationships between records. Activity reports are limited to the signed in user, which prevents users from viewing the private inventory activity of other accounts. Transactions and error handling also help the application fail safely instead of leaving incomplete or inconsistent data.

I also understand that the project would need more protection before being released as a production application. It would need secure hosting, encrypted network traffic, stronger cookie settings, request rate limits, monitoring, backups, and regular updates. Recognizing these limits is important because no application is ever completely secure or completely finish.

These improvements made inventory changes easier to track and helped protect the accuracy of the stored information. Although the enhancements are divided into separate categories, they support one another. The layered design provides an organized foundation. Search and pagination help the application remain useful as the database grows. Activity history and transactions make inventory changes easier to review and trust.

The code review explains the original project and the plan for improving it. The written narratives explain the decisions, challenges, and results in more detail. The original code, enhanced code, automated tests, code review, and narratives document the full development process from the beginning to the completed application. When I compare the original Android application with the completed browser application, I can see how much my approach has changed. The biggest improvement is not only the number of features. It is the way I now plan, organize, secure, test, and evaluate software solutions.

This portfolio represents the knowledge I gained throughout the Computer Science program, but it also connects to the work I already perform in warehouse automation. My professional experience gives me a practical understanding of the environment where I hope to use my software engineering skills. I am prepared to continue learning and growing into a software engineer who creates reliable, secure, and useful systems.

Algorithms and Data Structures Enhancement

This enhancement improved the way users search and move through large inventory lists.

Completed Enhancement

The application cleans the search value, removes unnecessary spaces, limits the search to 80 characters, and performs the search inside SQLite. The search is case insensitive and safely treats the percent sign, underscore, and backslash as normal text when the user enters them.

Ranking places an exact item name first, a name that begins with the search value second, and a name containing the value in another position after that. Pagination limits the results to ten records on each page and corrects page values that are outside the valid range. The InventorySearchPage and InventorySummary data structures keep related values together. Frozen data classes and tuple results help prevent accidental changes.

The database search and result sorting can be described as O(n + m log m), where n is the number of records examined and m is the number of matching records. Transferring the current page is O(k), where k is the small number of displayed records. Nine automated tests verified this stage of the application.

Database Enhancement

This enhancement added reliable activity history, reporting, privacy controls, and stronger database protection.

Completed Enhancement

I added an inventory activity table that records create, update, and delete actions. Each history record stores important inventory values so deleted or changed information can still be reviewed. Foreign keys and database constraints protect relationships and prevent invalid quantities.

Transactions keep an inventory change and its history record together. If either part fails, the full operation is rolled back. The dashboard report summarizes inventory activity for the signed in user while ownership checks protect the information of other users. Composite indexes improve common search and report requests.

The final application contains eleven passing automated tests. These tests verify account security, inventory operations, search behavior, pagination, transactions, activity history, reporting, privacy, and rollback behavior.
